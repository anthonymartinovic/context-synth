# Context Synth -- v0.1.0 Design

## Purpose

First end-to-end slice. Validates the full core loop from `docs/PROJECT_SPEC.md`: context → compilation → capability graph → resolution → projection.

DJ-V is the first example application built on Context Synth. It turns governed context (documents + audio reference tracks) into generative music. DJ-V is not part of the framework — it is a consumer of it. Its role in this release is to prove the architecture works end-to-end.

## Release Goal

Prove that governed context compiled from diverse sources can drive a dependency graph of external capabilities, resolved into a dynamic output — in this case, generative music.

The demo succeeds if:

- multiple context sources (documents + audio reference tracks) compile into a governed artifact
- the artifact drives a capability graph that resolves into music parameters
- music is generated that audibly changes when the context changes

## Architecture Tiers

This release establishes three tiers that remain distinct throughout the project:

**Framework** — Context Synth itself. Protocol, engine, runtime, and the interfaces that integrations and applications build against. Framework code does not know about audio formats, music, or DJ-V.

**Integrations** — implementations of framework interfaces for specific external systems. MP3 audio source adapter, markdown source adapter, and others over time. Integrations ship with the framework but are architecturally distinct from it. New integrations implement existing interfaces — they do not require framework changes.

**Example Applications** — applications built on the framework using integrations. DJ-V is the first. Example applications are not part of the framework or its integrations. They wire specific integrations together through the framework's protocol and runtime.

## Scope

### Framework

- Machine-readable context artifact format (JSON, protocol bridge between engine and runtime)
- `cs run` command for capability resolution and projection
- Minimal runtime with static graph construction and dependency resolution
- Adapter interface for projection
- Llama as the default LLM provider (replacing Gemini)
- `llm.Client` interface remains provider-agnostic

### Integrations

- MP3 audio source adapter (new, behind `source.Provider` interface)
- Existing markdown source adapter (unchanged)

### DJ-V (Example Application)

- Music adapter producing generative audio from resolved state
- Capability declarations wiring context interpretation to audio synthesis
- End-to-end example: documents + audio reference tracks → artifact → capability graph → generative music

### Excluded

- TypeScript SDK (deferred — SDK shape derived from experience building DJ-V)
- Dynamic capability discovery (capabilities statically declared)
- Multiple adapters per run
- Reactive or continuous runtime mode
- Production-grade music quality
- Stable protocol format commitment
- Capability failure handling and partial resolution

## CLI

Extends the existing CLI with a new command:


| Command    | Purpose                                                    |
| ---------- | ---------------------------------------------------------- |
| `cs init`  | Generate starter config                                    |
| `cs snap`  | Resolve sources, report snapshot                           |
| `cs synth` | Run the compilation pipeline, produce the context artifact |
| `cs run`   | Load artifact, resolve capability graph, project output    |


`cs run` flags: `--artifact`, `--adapter`, `--verbose`

The separation of `cs synth` and `cs run` makes the protocol boundary visible at the CLI level. The context artifact is the stable interface between them.

## Context Artifact Format

The artifact transitions from rendered markdown to a structured, machine-readable format. JSON for v0.1.0.

Requirements:

- Contains all governance metadata: provenance, weights, content hashes, omissions, budget, mode
- Self-describing — the runtime consumes it without knowledge of how it was produced
- Stable interface between engine and runtime

```json
{
  "meta": {
    "generator": "cs v0.1.0",
    "mode": "full",
    "snapshot_hash": "...",
    "config_hash": "...",
    "timestamp": "...",
    "budget": 10000,
    "tokens_used": 8742
  },
  "sections": [
    {
      "name": "Musical Context",
      "items": [
        {
          "content": "...",
          "source": "sources/mp3/midnight_drive.mp3",
          "weight": 0.9,
          "content_hash": "...",
          "token_count": 340
        }
      ]
    }
  ],
  "omissions": [
    {
      "source": "...",
      "reason": "exceeded budget",
      "weight": 0.6,
      "token_count": 1200
    }
  ]
}
```

The artifact format is explicitly unstable in v0.1.0. It is a working format, not a protocol commitment.

## Llama Integration

Replaces Gemini as the default LLM provider.

- New `LlamaClient` implementation behind the existing `llm.Client` interface
- Used in both the engine (extraction/classification) and the runtime (context interpretation)
- Local model inference — no proprietary API dependency
- The `llm.Client` interface remains provider-agnostic; Gemini and other providers stay available as alternatives

## MP3 Audio Source Adapter (Integration)

New source adapter behind the existing `source.Provider` interface. This is an integration, not framework core — it implements the framework's source interface for local audio files.

Each audio file is declared as an individual source with its own explicit weight. There is no playlist or directory abstraction — the user places reference tracks in a local folder and declares each one. This gives full control over which tracks influence the output and by how much.

- Each audio file is analyzed by librosa during the Snap phase using HPSS (harmonic-percussive source separation) for accurate feature extraction
- Each track item contains: filename, tempo (from percussive component), key and mode (from harmonic component), energy, danceability, valence, loudness, spectral contrast, spectral rolloff, tonnetz, MFCCs, zero crossing rate, harmonic-to-percussive energy ratio
- Provenance per track: file path, content hash
- No external API dependency — analysis runs locally via a Python script
- Analyzer path configured via `CS_AUDIO_ANALYZER` environment variable

Configuration:

```yaml
sources:
  - markdown: sources/md/vibe.md
    weight: 1.0
  - mp3: sources/mp3/midnight_drive.mp3
    weight: 0.8
  - mp3: sources/mp3/neon_pulse.mp3
    weight: 0.7
  - mp3: sources/mp3/deep_current.mp3
    weight: 0.6

sections:
  - name: Musical Context
    budget: 0.50
  - name: Creative Direction
    budget: 0.30
  - name: Constraints
    budget: 0.20

llm:
  provider: llama
  model: llama3.1:8b
```

## DJ-V: Capability Graph

DJ-V declares its own capabilities and wires them through the framework's runtime. These are DJ-V's capability declarations, not the framework's.

Capabilities are statically declared for v0.1.0. No dynamic discovery.

External capabilities involved:

- **Llama** — interprets compiled context into music parameters
- **Audio synthesis** — generates music from parameters

Dependency graph:

```
context_artifact
        │
        ▼
interpret_context
(Llama derives music parameters from governed context:
 tempo, key, mood, energy, instrumentation hints)
        │
        ▼
generate_audio
(synthesis engine produces generative audio
 from the derived parameters)
        │
        ▼
output
(audio playback)
```

Resolution is single-shot for v0.1.0: resolve once, project once.

### Music Parameters

The `interpret_context` capability produces a structured parameter set derived from the governed context — both document content and audio analysis features. Source weight influences how strongly each input shapes the parameters.

```json
{
  "tempo_bpm": 120,
  "key": "C",
  "mode": "minor",
  "energy": 0.7,
  "mood": "melancholic",
  "density": 0.5,
  "instrumentation": ["synth_pad", "drums", "bass"]
}
```

## DJ-V: Music Generation

DJ-V uses two components for audio output:

**MusicGen subprocess** (`scripts/generate.py`) — receives music parameters (derived by the `interpret_context` capability) and generates a 15-second WAV file using Meta's MusicGen model (`facebook/musicgen-small`). The `description` field from the music parameters drives generation via text-conditioned synthesis. When a melody audio path is provided, it uses `facebook/musicgen-melody` for melody-conditioned generation instead.

**Adapter** (`adapter/src/index.ts`) — a thin Deno script that implements the framework's adapter interface. It receives `ResolvedState` from stdin, locates the generated audio file in the outputs, and plays it using the platform's built-in audio player (`afplay` on macOS, `aplay` on Linux).

The original design considered Tone.js for procedural synthesis. MusicGen was chosen instead because text-conditioned ML generation produces more musically coherent output from natural language descriptions, which better demonstrates that governed context materially shapes the output.

- ML-based audio generation driven by context-derived descriptions and parameters
- The music is recognizably different when context changes — different reference tracks and documents produce different descriptions, which produce different music
- Quality target: functional and demonstrative, not production-grade
- Output: 15-second WAV file with automatic playback

The adapter demonstrates projection independence: it renders resolved state without influencing how that state was produced. A different adapter could take the same resolved state and produce a visualization, a dashboard, or anything else.

## Acceptance Criteria

### Framework

1. The context artifact is machine-readable JSON with full governance metadata (provenance, weights, hashes, omissions).
2. `cs synth` and `cs run` operate independently across the artifact boundary.
3. The runtime constructs a capability graph from the artifact and resolves it in dependency order.
4. Llama is the default LLM provider for both compilation and resolution.
5. Source traceability, weight influence, and boundedness survive from compilation through resolution.

### DJ-V

1. Audio reference tracks and markdown documents compile into a governed context artifact.
2. The artifact drives a capability graph that resolves into music parameters.
3. Music is generated that is audibly different when context changes.
4. Changing source weights produces different music parameters.
5. The full pipeline runs end-to-end: `cs synth` → artifact → `cs run` → music.

## Deferred

- TypeScript SDK (shape to be derived from DJ-V adapter experience)
- Dynamic capability discovery
- Multiple simultaneous adapters
- Reactive or continuous runtime mode
- Stable protocol format commitment
- Advanced music generation (multi-track, arrangement, real-time manipulation)
- Graph visualization and debugging tools
- Capability failure semantics and partial resolution
