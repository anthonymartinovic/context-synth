# Context Synth -- v0.1.0 Design

## Purpose

First end-to-end slice. Validates the full core loop from `docs/PROJECT_SPEC.md`: context → compilation → capability graph → resolution → projection.

DJ-V is the first product built on Context Synth. It turns governed context (documents + a Spotify playlist) into generative music. DJ-V is not part of the framework — it is a consumer of it. Its role in this release is to prove the architecture works end-to-end.

## Release Goal

Prove that governed context compiled from diverse sources can drive a dependency graph of external capabilities, resolved into a dynamic output — in this case, generative music.

The demo succeeds if:

- multiple context sources (documents + Spotify playlist) compile into a governed artifact
- the artifact drives a capability graph that resolves into music parameters
- music is generated that audibly changes when the context changes

## Architecture Tiers

This release establishes three tiers that remain distinct throughout the project:

**Framework** — Context Synth itself. Protocol, engine, runtime, and the interfaces that integrations and products build against. Framework code does not know about Spotify, music, or DJ-V.

**Integrations** — implementations of framework interfaces for specific external systems. Spotify source adapter, markdown source adapter, and others over time. Integrations ship with the framework but are architecturally distinct from it. New integrations implement existing interfaces — they do not require framework changes.

**Products** — applications built on the framework using integrations. DJ-V is the first. Products are not part of the framework or its integrations. They wire specific integrations together through the framework's protocol and runtime.

## Scope

### Framework

- Machine-readable context artifact format (JSON, protocol bridge between engine and runtime)
- `cs run` command for capability resolution and projection
- Minimal runtime with static graph construction and dependency resolution
- Adapter interface for projection
- Llama as the default LLM provider (replacing Gemini)
- `llm.Client` interface remains provider-agnostic

### Integrations

- Spotify playlist source adapter (new, behind `source.Provider` interface)
- Existing markdown source adapter (unchanged)

### DJ-V (Product)

- Music adapter producing generative audio from resolved state
- Capability declarations wiring context interpretation to audio synthesis
- End-to-end example: documents + Spotify playlist → artifact → capability graph → generative music

### Excluded

- TypeScript SDK (deferred — SDK shape derived from experience building DJ-V)
- Dynamic capability discovery (capabilities statically declared)
- Multiple adapters per run
- Reactive or continuous runtime mode
- Production-grade music quality
- Stable protocol format commitment
- Capability failure handling and partial resolution

## CLI

Extends the existing CLI with a new command:


| Command    | Purpose                                                    |
| ---------- | ---------------------------------------------------------- |
| `cs init`  | Generate starter config                                    |
| `cs snap`  | Resolve sources, report snapshot                           |
| `cs synth` | Run the compilation pipeline, produce the context artifact |
| `cs run`   | Load artifact, resolve capability graph, project output    |


`cs run` flags: `--artifact`, `--adapter`, `--verbose`

The separation of `cs synth` and `cs run` makes the protocol boundary visible at the CLI level. The context artifact is the stable interface between them.

## Context Artifact Format

The artifact transitions from rendered markdown to a structured, machine-readable format. JSON for v0.1.0.

Requirements:

- Contains all governance metadata: provenance, weights, content hashes, omissions, budget, mode
- Self-describing — the runtime consumes it without knowledge of how it was produced
- Stable interface between engine and runtime

```json
{
  "meta": {
    "generator": "cs v0.1.0",
    "mode": "full",
    "snapshot_hash": "...",
    "config_hash": "...",
    "timestamp": "...",
    "budget": 10000,
    "tokens_used": 8742
  },
  "sections": [
    {
      "name": "Musical Context",
      "items": [
        {
          "content": "...",
          "source": "spotify:playlist:37i9dQZF1DXcBWIGoYBM5M",
          "weight": 0.9,
          "content_hash": "...",
          "token_count": 340
        }
      ]
    }
  ],
  "omissions": [
    {
      "source": "...",
      "reason": "exceeded budget",
      "weight": 0.6,
      "token_count": 1200
    }
  ]
}
```

The artifact format is explicitly unstable in v0.1.0. It is a working format, not a protocol commitment.

## Llama Integration

Replaces Gemini as the default LLM provider.

- New `LlamaClient` implementation behind the existing `llm.Client` interface
- Used in both the engine (extraction/classification) and the runtime (context interpretation)
- Local model inference — no proprietary API dependency
- The `llm.Client` interface remains provider-agnostic; Gemini and other providers stay available as alternatives

## Spotify Source Adapter (Integration)

New source adapter behind the existing `source.Provider` interface. This is an integration, not framework core — it implements the framework's source interface for a specific external system.

The Spotify adapter supports two declaration styles:

**Playlist** — declared as a single source. The adapter expands it into individual track items during the Snap phase, each with its own weight, audio features, and provenance. Tracks compete for budget individually; omitted tracks are recorded in the artifact's omissions table with full traceability.

**Individual tracks** — declared directly as sources with explicit weights. Use this when you want manual control over which tracks influence the output and by how much.

Both styles normalize into the same source-type-agnostic representation. They can be mixed — a playlist for the bulk, plus individual tracks weighted to guarantee specific influence.

- Fetches playlist and/or track data via Spotify Web API
- Each track item contains: track name, artist, audio features (tempo, energy, danceability, valence, key, mode, loudness)
- Provenance per track: playlist URI (if from a playlist), track ID, position (if from a playlist), fetch timestamp
- Authentication via environment variables (client credentials flow)

### Playlist Track Weighting

When a playlist is declared as a source, track weight is position-based. The first track in the playlist receives the playlist's declared weight. Subsequent tracks decay proportionally from there. This respects playlist curation order — earlier tracks have more influence over the output.

The exact decay curve is an implementation detail, but the invariant is: position 1 has the most influence, position N has the least.

Configuration:

```yaml
sources:
  - path: sources/vibe.md
    weight: 1.0
  - path: sources/constraints.md
    weight: 0.9
  - spotify: playlist:37i9dQZF1DXcBWIGoYBM5M
    weight: 0.8
    track_weight: position
  - spotify: track:4uLU6hMCjMI75M1A2tKUQC
    weight: 1.0

sections:
  - name: Musical Context
    budget: 0.50
  - name: Creative Direction
    budget: 0.30
  - name: Constraints
    budget: 0.20

llm:
  provider: llama
  model: llama-3.3-70b
```

## DJ-V: Capability Graph (Product)

DJ-V declares its own capabilities and wires them through the framework's runtime. These are DJ-V's capability declarations, not the framework's.

Capabilities are statically declared for v0.1.0. No dynamic discovery.

External capabilities involved:

- **Llama** — interprets compiled context into music parameters
- **Audio synthesis** — generates music from parameters

Dependency graph:

```
context_artifact
        │
        ▼
interpret_context
(Llama derives music parameters from governed context:
 tempo, key, mood, energy, instrumentation hints)
        │
        ▼
generate_audio
(synthesis engine produces generative audio
 from the derived parameters)
        │
        ▼
output
(audio playback)
```

Resolution is single-shot for v0.1.0: resolve once, project once.

### Music Parameters

The `interpret_context` capability produces a structured parameter set derived from the governed context — both document content and Spotify audio features. Source weight influences how strongly each input shapes the parameters.

```json
{
  "tempo_bpm": 120,
  "key": "C",
  "mode": "minor",
  "energy": 0.7,
  "mood": "melancholic",
  "density": 0.5,
  "instrumentation": ["synth_pad", "drums", "bass"]
}
```

## DJ-V: Music Adapter (Product)

Receives resolved state (music parameters) and produces generative audio. This is a DJ-V component — it implements the framework's adapter interface but is not part of the framework.

- Procedural audio generation driven by context-derived parameters
- Implementation in TypeScript using Tone.js or equivalent synthesis library
- The music is recognizably different when context changes — different playlists and documents produce different music
- Quality target: functional and demonstrative, not production-grade
- Output: real-time audio playback or rendered audio file

The adapter demonstrates projection independence: it renders resolved state without influencing how that state was produced. A different adapter could take the same resolved state and produce a visualization, a dashboard, or anything else.

## Acceptance Criteria

### Framework

1. The context artifact is machine-readable JSON with full governance metadata (provenance, weights, hashes, omissions).
2. `cs synth` and `cs run` operate independently across the artifact boundary.
3. The runtime constructs a capability graph from the artifact and resolves it in dependency order.
4. Llama is the default LLM provider for both compilation and resolution.
5. Source traceability, weight influence, and boundedness survive from compilation through resolution.

### DJ-V

1. A Spotify playlist and markdown documents compile into a governed context artifact.
2. The artifact drives a capability graph that resolves into music parameters.
3. Music is generated that is audibly different when context changes.
4. Changing source weights produces different music parameters.
5. The full pipeline runs end-to-end: `cs synth` → artifact → `cs run` → music.

## Deferred

- TypeScript SDK (shape to be derived from DJ-V adapter experience)
- Dynamic capability discovery
- Multiple simultaneous adapters
- Reactive or continuous runtime mode
- Stable protocol format commitment
- Advanced music generation (multi-track, arrangement, real-time manipulation)
- Graph visualization and debugging tools
- Capability failure semantics and partial resolution
