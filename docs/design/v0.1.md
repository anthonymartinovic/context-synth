# Context Synth -- v0.1 Design

## Purpose

This document defines the implementation target for Context Synth v0.1. It is intentionally narrower and more opinionated than `docs/VISION.md`. The goal is to validate the core workflow without freezing the full long-term product shape.

## Release Goal

v0.1 should prove that Context Synth can take configured source documents, compile them into a bounded context artifact, and preserve enough provenance for a human to inspect what the agent was given.

The release is successful if it validates the workflow, not if it solves every long-term design question.

## v0.1 Scope

### Included

- single-binary CLI: `cs`
- local markdown files as the only source type
- config-driven section and budget definitions
- deterministic source capture
- bounded artifact generation
- source traceability for included content
- deterministic fallback mode when no LLM is configured
- optional LLM-backed extraction, ranking, and verification behind internal interfaces

### Excluded

- MCP-backed ingestion
- non-markdown source types
- rich caching or incremental regeneration
- provider-specific optimization beyond what is needed to make the pipeline work
- CI integrations, artifact diffing, or drift detection
- a permanently stable artifact format

## Primary Workflow

The primary workflow for v0.1 is:

1. A repository maintainer defines sections and source documents in `contextsynth.yml`.
2. The maintainer runs `cs synth`.
3. Context Synth captures the configured markdown sources, assembles a bounded context artifact, and records source provenance.
4. A human can inspect the artifact and the attached metadata before giving it to an agent or committing it to the repository.

This release is optimized for agent-assisted implementation work in repositories where important context lives in docs rather than code alone.

## CLI Surface

Distributed as a single binary: `cs`.

### `cs init`

Generates a starter `contextsynth.yml`.

### `cs snap`

Resolves configured source paths and reports the source set that would be used for synthesis.

### `cs synth`

Runs the synthesis pipeline and writes the context artifact.

Representative flags:

- `--config <path>`
- `--output <path>`
- `--verbose`
- `--dry-run`
- `--no-llm`

## Configuration

### Default Schema

```yaml
version: "1"

output:
  path: context.md

budget: 10000

llm:
  extract:
    provider: gemini
    model: gemini-2.5-pro
    api_key_env: GEMINI_API_KEY
  rank:
    provider: gemini
    model: gemini-2.0-flash
    api_key_env: GEMINI_API_KEY
  verify:
    provider: gemini
    model: gemini-2.0-flash
    api_key_env: GEMINI_API_KEY

sections:
  - name: Domain Knowledge
    sources:
      - docs/domain/overview.md
      - docs/domain/glossary.md
    budget: 0.30

  - name: Architecture Decisions
    sources:
      - docs/adrs/*.md
    budget: 0.25

  - name: Requirements
    sources:
      - docs/requirements/*.md
    budget: 0.25

  - name: Constraints
    sources:
      - docs/constraints.md
    budget: 0.20
```

### Rules

- `version` must be `"1"`
- `output.path` defaults to `context.md`
- `budget` is a total token budget for the artifact
- section `budget` values are proportional weights normalized at runtime
- source paths are relative to the config file
- glob patterns are supported
- `llm` is optional

## Pipeline

v0.1 follows a five-stage pipeline:

| Stage | Role |
|-------|------|
| `Snap` | Capture and normalize configured markdown sources |
| `Extract` | Produce candidate context items from those sources |
| `Rank` | Order candidates within each section |
| `Assemble` | Build the final artifact within the configured budget |
| `Verify` | Check whether included derived items remain aligned with their sources |

### Stage Expectations

- `Snap` is deterministic.
- `Assemble` is deterministic.
- `Extract`, `Rank`, and `Verify` may be LLM-backed.
- All included derived items must preserve provenance back to captured source material.

## Fallback Mode

When no LLM is configured, or when `--no-llm` is set:

- extraction, ranking, and verification are skipped
- source contents are assembled in config order within budget
- source tracking still records what was included or omitted

This is the minimum viable governance mode for the first release.

## Artifact Requirements

v0.1 intentionally defines artifact properties more than a permanent presentation format.

The generated artifact must:

- be markdown by default
- be bounded by the configured budget
- preserve section structure from config
- surface enough metadata for a human to understand where included context came from
- record artifact-level metadata such as generator version, source snapshot identity, config identity, token count, and operating mode

The exact rendered shape may evolve after v0.1. What matters for the release is that the artifact is bounded, traceable, and reviewable.

## Provenance And Verification

v0.1 should attach enough provenance for a human to answer:

- what source produced an included item
- what source material was omitted due to budget or ranking
- what verification outcome was recorded for an included derived item
- which exact source snapshot the artifact came from

Verification in v0.1 is an alignment check, not a proof system. It should increase confidence in derived items without pretending to guarantee semantic correctness.

## Acceptance Criteria

v0.1 is complete when:

1. A user can configure local markdown sources and generate a context artifact with `cs synth`.
2. The artifact stays within the configured budget.
3. Included content remains traceable to specific source material.
4. `cs snap` makes the captured source set inspectable before synthesis.
5. `cs synth --no-llm` still produces a useful governed artifact.
6. The pipeline keeps the source-capture boundary clean enough that future MCP-backed sources can be added as a new ingestion adapter rather than a pipeline rewrite.

## Deferred Questions

These questions remain intentionally open beyond v0.1:

- the final stable source-reference model
- the final rendered artifact format or sidecar structure
- richer multi-source verification semantics
- incremental regeneration and caching strategy
- MCP-backed ingestion details
