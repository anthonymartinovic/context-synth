# Context Synth -- v0.1.0 Reflection

## What This Version Set Out To Do

Prove that governed context compiled from diverse sources can drive a dependency graph of external capabilities, resolved into a dynamic output. DJ-V — documents and audio reference tracks compiled into a governed artifact, driving a capability graph that resolves into generative music — was the vehicle for that proof.

## What It Validated

### Framework

- The three-tier architecture holds: protocol defines contracts, engine compiles context, runtime resolves capabilities. The tiers communicate through the protocol and do not know each other's internals.
- The context artifact is a working protocol boundary between compilation and resolution. `cs synth` and `cs run` operate independently across it.
- JSON artifact format carries full governance metadata — provenance, weights, content hashes, omissions, budget, mode — through from compilation to resolution.
- Source traceability and weight influence survive end-to-end. Changing source weights visibly changes the artifact contents and downstream capability outputs.
- Llama as a local open-source LLM provider works for both compilation (extraction/classification) and resolution (context interpretation). No proprietary API dependency.
- The source provider interface (markdown, audio) extends without pipeline changes. Adding audio was a new integration, not a framework modification.
- Deterministic fallback preserves governance properties without an LLM.
- Capability graph construction, topological resolution, and executor dispatch (LLM + subprocess) work as designed.

### DJ-V

- Audio reference tracks analyzed by librosa (HPSS-based feature extraction) and markdown documents compile into a single governed artifact.
- The artifact drives a two-node capability graph: `interpret_context` (Llama) → `generate_audio` (MusicGen).
- Different context sources and different weight configurations produce different music parameters, which produce different audio.
- The full pipeline runs end-to-end: `cs synth` → artifact → `cs run` → music playback.

## Design Evolutions

### MusicGen over Tone.js

The original design specified Tone.js for procedural audio synthesis. During implementation, MusicGen (Meta's text-conditioned music generation model) replaced it. This was the right decision: MusicGen generates musically coherent audio from natural language descriptions, which better demonstrates that governed context materially shapes the output. Tone.js procedural synthesis would have required a complex parameter-to-sound mapping layer that would have been the actual engineering challenge — obscuring the framework's contribution.

The adapter became a thin Deno script that plays the generated audio rather than a synthesis engine. This is cleaner: the framework and runtime do the interesting work (governance, graph resolution), and the adapter just projects the result.

### Capability declarations as application config

Capabilities live in a static JSON file provided by the application, not discovered dynamically. This was the right scoping decision for v0.1.0. It keeps the framework's responsibility clear: it resolves a declared graph, it does not decide what goes in the graph. Dynamic discovery is a future concern.

## What Was Deferred

- TypeScript SDK — shape to be derived from DJ-V adapter experience
- Dynamic capability discovery
- Multiple simultaneous adapters
- Reactive or continuous runtime mode
- Stable protocol format commitment
- Capability failure handling and partial resolution
- Graph visualization and debugging tools

## What Did Not Work Well

- MusicGen on Apple Silicon MPS hits an EnCodec decoder limitation (conv1d > 65536 channels). Generation falls back to CPU, which is significantly slower (~2 minutes for 30 seconds of audio). This is a PyTorch/MPS constraint, not a framework issue.
- Audio analysis with librosa on 4 MP3 files takes ~2 minutes. For a demo this is acceptable; for any real workflow it would need caching or parallelism.
- The verification surface exists but is minimal — it reports included/omitted items with source paths and weights. It does not yet support policy-aware verification or structured review workflows.

## Position

v0.1.0 proves the core loop. Governed context compiled from diverse sources drives a capability graph that resolves into a dynamic output. The framework provided the infrastructure; the example application (DJ-V) provided the declarations and adapter. Neither knew the other's internals.

The next version should focus on making the framework consumable by external systems — SDK, stable protocol contracts, richer capability semantics — rather than on making DJ-V more sophisticated. DJ-V has served its purpose as the proof vehicle.
