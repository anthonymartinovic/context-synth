# Context Synth -- v0.1.0 Implementation Plan

## Overview

This plan breaks the v0.1.0 build into five milestones ordered by dependency. The critical path is M1–M3: after M3, the full framework (protocol, engine, runtime) is functional. M4 builds DJ-V as the first product on top of the framework. M5 validates everything end-to-end.

Design decisions are recorded in `docs/design/v0.1.0.md`.

### Key Design Choices

- `model/` is renamed to `protocol/`. These types are the contracts between engine and runtime — artifact format, capability declarations, adapter interface. The name reflects their role.
- `internal/` contains only framework core — interfaces, engine pipeline stages, runtime orchestration, and executor mechanisms. No integration-specific code.
- `integrations/` contains implementations of framework interfaces for specific external systems, grouped by interface type. `integrations/source/` for source adapters, `integrations/llm/` for LLM providers. Integrations are importable by external consumers.
- `examples/` contains products built on the framework. DJ-V is the first.
- `cmd/cs/main.go` is the composition root. It reads config, creates the appropriate integration instances (Llama client, Spotify adapter, etc.), and passes them to the engine and runtime. This is the only place that imports specific integrations.
- Flat package structure within `internal/`. Architecture (protocol/engine/runtime) is enforced through interfaces, not directory nesting. Go convention.

### Adapter Interface

```go
type Adapter interface {
    Project(ctx context.Context, state ResolvedState) error
}
```

The subprocess adapter implementation invokes an external process, passes the resolved state as JSON on stdin, and streams output. This is how the Go runtime communicates with the TypeScript music adapter.

### Capability Declaration

```go
type Capability struct {
    ID           string
    Description  string
    Inputs       []string
    Outputs      []string
    DependsOn    []string
    Executor     ExecutorSpec
}

type ExecutorSpec struct {
    Type   string          // "llm" or "subprocess"
    Config json.RawMessage // executor-specific configuration
}
```

For v0.1.0, capability declarations are loaded from a static JSON file. No dynamic discovery. Two executor types are supported: LLM (sends a prompt, receives structured output) and subprocess (invokes an external process with JSON on stdin).

Executor configuration is product-provided. The framework provides the executor mechanisms; products provide the declarations that wire those mechanisms to specific tasks. For example, DJ-V's `capabilities.json` specifies the prompt template for `interpret_context` and the subprocess command for `generate_audio` — the framework never sees or cares about music-specific content.

## Milestones

### M1: Protocol

**Goal:** Define and codify the contracts between engine, runtime, and adapters. Restructure packages to reflect the three-tier model.

| Work Item | Location | Notes |
|-----------|----------|-------|
| Rename `model/` to `protocol/` | `internal/protocol/` | Move existing types, update all imports |
| Move markdown adapter | `integrations/source/markdown/` | Extract from `internal/source/`, implement `source.Provider` |
| Move wiring to composition root | `cmd/cs/` | CLI creates integration instances, passes to pipeline |
| Artifact JSON serialization | `internal/protocol/` | `Artifact` serializes to/from JSON. Replaces markdown as default output. |
| Capability declaration types | `internal/protocol/` | `Capability` struct with ID, inputs, outputs, dependencies, executor spec |
| Executor spec types | `internal/protocol/` | `ExecutorSpec` with type and config |
| Adapter interface | `internal/protocol/` | `Adapter` interface with `Project(ctx, ResolvedState) error` |
| Resolved state type | `internal/protocol/` | `ResolvedState` — the output of graph resolution, input to adapters |
| Update `render/` | `internal/render/` | Output JSON instead of markdown |
| Update `pipeline/` | `internal/pipeline/` | Accept `llm.Client` as a parameter instead of creating it. Produce JSON artifact. |
| Update `cs synth` | `cmd/cs/` | Write JSON artifact to output path |

**Tests:** Artifact round-trips through JSON (serialize → deserialize → compare). Existing pipeline tests pass after restructure. `cs synth` produces valid JSON. Markdown integration still works from its new location.

---

### M2: Engine

**Goal:** The engine compiles diverse sources into a protocol-compliant artifact using an open-source model.

| Work Item | Location | Notes |
|-----------|----------|-------|
| Llama client | `integrations/llm/llama/` | `LlamaClient` implementing `llm.Client`. Talks to ollama HTTP API. |
| Update CLI wiring | `cmd/cs/` | Read `provider` from config, create Llama client. |
| Spotify source adapter | `integrations/source/spotify/` | Implements `source.Provider`. Fetches playlist/track data via Spotify Web API. |
| Track expansion | `integrations/source/spotify/` | Playlist declared as single source, adapter expands into individual track items during Snap. |
| Position-based weighting | `integrations/source/spotify/` | First track gets playlist weight, subsequent tracks decay. |
| Individual track support | `integrations/source/spotify/` | `spotify: track:ID` as a direct source declaration with explicit weight. |
| Config updates | `internal/config/` | Support `spotify:` source type, `track_weight` field, `provider: llama` |

**Tests:** Llama client completes a prompt via ollama (gated behind env var). Spotify adapter returns track data for a known playlist (gated behind env var). Track expansion produces N sources from a playlist. Position weighting decays correctly. Config validates Spotify and Llama declarations.

---

### M3: Runtime

**Goal:** The runtime loads a context artifact, constructs a capability graph, resolves it using executor mechanisms, and invokes an adapter. `cs run` works.

| Work Item | Location | Notes |
|-----------|----------|-------|
| Graph construction | `internal/graph/` | Load capability declarations from JSON. Build directed graph. Validate no cycles. |
| Dependency resolution | `internal/graph/` | Topological sort. Resolve capabilities in dependency order. |
| LLM executor | `internal/runtime/` | Dispatches to `llm.Client` with prompt from capability's executor config. Produces structured output. |
| Subprocess executor | `internal/runtime/` | Spawns external process, pipes input as JSON on stdin, captures output. |
| Runtime orchestrator | `internal/runtime/` | `Run(ctx, artifact, capabilities, adapter) error` — build graph, resolve each capability via its executor, produce `ResolvedState`, invoke adapter. |
| Subprocess adapter | `internal/adapter/` | Implements `protocol.Adapter`. Spawns external process, pipes `ResolvedState` on stdin. |
| `cs run` command | `cmd/cs/` | Flags: `--artifact`, `--adapter`, `--verbose`. Loads artifact, loads capabilities, creates LLM client, invokes runtime. |

**Tests:** Graph construction from capability JSON. Cycle detection rejects invalid graphs. Topological sort produces correct resolution order. LLM executor sends prompt and parses response (mock client). Subprocess executor invokes a test script and receives JSON. `cs run` loads an artifact and invokes a stub adapter.

**After M3:** The framework is complete. Protocol defines contracts. Engine compiles context into artifacts. Runtime resolves capability graphs via executor mechanisms and projects output. All three components communicate through the protocol. The CLI wires integrations at the composition root.

---

### M4: DJ-V

**Goal:** The first product runs end-to-end. Documents + Spotify playlist → governed artifact → capability graph → generative music.

| Work Item | Location | Notes |
|-----------|----------|-------|
| Capability declarations | `examples/dj-v/capabilities.json` | `interpret_context` (LLM executor with music-specific prompt template) → `generate_audio` (subprocess executor invoking the TypeScript adapter) |
| Music adapter | `examples/dj-v/adapter/` | TypeScript + Tone.js. Reads `ResolvedState` JSON from stdin. Generates procedural audio. |
| `interpret_context` prompt | `examples/dj-v/capabilities.json` | DJ-V-specific prompt that tells Llama to derive music parameters (tempo, key, mood, energy, instrumentation) from governed context |
| Example context sources | `examples/dj-v/sources/` | `vibe.md`, `constraints.md` — example creative direction for the DJ |
| Example config | `examples/dj-v/contextsynth.yml` | Sources (markdown + Spotify playlist), sections, Llama config |
| End-to-end run script | `examples/dj-v/` | `cs synth` → artifact → `cs run --adapter "node adapter/dist/index.js"` → music |

**Tests:** `cs synth` with DJ-V config produces a valid artifact containing Spotify track data and document extractions. `cs run` invokes the music adapter and produces audio. Different context sources produce different music parameters. Changing source weights changes the parameters.

**After M4:** DJ-V works. The full loop is proven: context → compilation → capability graph → resolution → generative music. The framework provided the infrastructure; DJ-V provided the declarations and adapter.

## Build Order Summary

```
M1  Protocol                          ← contracts defined, packages restructured, JSON artifact works
M2  Engine                            ← Llama + Spotify integrations, diverse sources compile
M3  Runtime                           ← graph resolves, executors dispatch, cs run works
M4  DJ-V                              ← first product, full loop proven
M5  Polish + Validation               ← all ACs validated, errors handled
```

M1–M3 is the critical path. After M3, the framework is functional. M4 builds the product that proves it. M5 validates and polishes.
